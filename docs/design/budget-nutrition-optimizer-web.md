## 1. 背景

`docs/analysis/health-app-b2b-monetization-2026-09.md` 的结论是：消费端 B2C 攒人群 + B2B 分成变现在 solo dev 规模下期望值为负（全成本口径 −RM 39,779），
唯一可能成立的路径是 §7 的反转方案 —— **把「预算约束下的营养优化」当工具卖给已有人群的渠道方（企业健康计划 / 保险 wellness 模块）**。

那份分析里最关键的未知量是：**马来西亚渠道方到底认不认这个价值**。这个问题不能靠继续查资料回答，只能靠拿着东西去谈。
本工具就是那个「东西」。

**它有两个目的，优先级不同：**

1. **主要 —— B2B 洽谈的演示资产。** 一个能打开的 URL，比一份 slide 有说服力。没有它，洽谈只能讲概念。
2. **次要 —— 消费端需求信号。** 有人用、用得下去，是弱证据；没人用，是强反证。

**不在范围内：**

- 移动端 App（分析文档明确结论：渠道方表达真实兴趣之前不投那 270 小时）
- 用户账号、登录、任何服务端持久化 —— 这是**刻意的设计约束**，见 §9
- 个性化营养建议 —— 受 Act 774 限制，定位必须是「价格与宏量的算术」，见 §9
- 数据集从 48 条扩到 300 条 —— 那是 App 阶段的工作，验证阶段先用现有数据

## 3. 现状与既有约束

```text
datasets/nutrition/{foods,prices}/*.yaml   ← 48 条食物 / 46 条马币价格 / 45 条微量营养素
        │
        ├──→ scripts/generate-nutrition-docs.mjs  ── 仅机械渲染 ──→ MDX 目录页
        │                                                              └─→ FoodsExplorer（食物→营养 表格）
        │                                                              └─→ NutrientLookup（营养→食物 排名）
        │
        └──→ scripts/lib/nutrition/（personal-os, Python）── food_lookup 派生宏量与成本
```

**两条现有组件都是查询工具，不回答决策问题。** `NutrientLookup` 按营养**密度**（每 100g 含量）排名，
不是按**每林吉特含量**排名 —— 这正是分析文档 §7 认定的差异化轴，也是本工具唯一要补的核心计算。

**必须遵守的既有不变量**（`generate-nutrition-docs.mjs` 文件头，逐字）：

> Mechanical rendering + display-label lookups only. **No macro or cost arithmetic: that's `scripts/nutrition.py`'s job in personal-os — one derivation implementation, not two that can drift apart.**

优化器本质是成本运算。**直接写成 Docusaurus 里的 JS 组件会违反这条不变量** —— 届时 `parse_cost` 的
「`~` 为估算标记、取值时剥离」这类约定会在 Python 和 TS 各存一份，正是该不变量要防的漂移。§4 的设计绕开这一点。

**现有局限（事实，非抱怨）**
- `FoodsExplorer` 的 `priceValue` 已是数值字段、已可排序，但没有任何「营养 ÷ 价格」的派生列。
- `rda_reference.yaml` 明确声明取的是**通用 US/EU Daily Value**，不是马来西亚 RNI。见 §10 开放问题 2。
- 食物名为 `鸡蛋 (egg)` 这类中英混排。见 §10 开放问题 5。

## 4. 提议架构

```text
datasets/nutrition/*.yaml
        │
        ↓
scripts/lib/nutrition/efficiency.py   [NEW]  ── 唯一的派生实现
   · 每克蛋白质成本  · 每 100% DV 各微量营养素成本  · 统一 basis 归一
        │
        ↓  make nutrition-export
nutrition-derived.json                [NEW]  ── 构建产物，已派生好的数值
        │
        ↓
repos/notes/src/lib/optimizer.ts      [NEW]  ── 纯 TS，只做组合搜索，不做派生
        │
        ├──→ BudgetOptimizer.tsx      [NEW]   预算 + 目标 → 推荐采购组合
        └──→ FoodsExplorer.tsx        [MODIFIED]  增加 RM/单位营养 列
```

> **设计意图：派生留在 Python，搜索放在 TS。** 这不是把同一个计算写两遍 ——
> 「每克蛋白质多少钱」是派生（Python 独占），「在预算内怎么组合」是在已派生数值上的搜索（TS）。
> 两者是不同计算，不构成不变量所禁止的重复实现。

| 组件 | 变更 | 理由 |
|------|------|------|
| `efficiency.py` | 新增派生模块 | 遵守既有不变量：成本运算只有一处实现 |
| `nutrition-derived.json` | 新增构建产物 | 让 TS 侧消费已派生的数值，而不是自己重算 |
| `optimizer.ts` | 新增纯函数模块 | 无框架依赖 → 未来抬进独立 Next.js 应用是复制，不是重写 |
| `BudgetOptimizer.tsx` | 新增 UI | 承载「我有 RM X，该买什么」这个决策问题 |
| `FoodsExplorer.tsx` | 增加派生列 | 2 小时的改动，让现有表格也带上差异化轴 |

## 5. 核心业务逻辑：优化问题的形式化

这是本工具的实质，必须写成规则而不是散文。

**输入**
- `budget_myr_per_day` — 每日预算（RM）
- `targets` — 目标集合，每项为 `{nutrient, min, max?}`；至少含 `protein_g` 与 `kcal`
- `excluded_food_ids` — 忌口/不吃的排除项

**求解**：在满足全部目标的前提下最小化总成本 —— 经典 Stigler diet 线性规划。

```
minimize    Σ  cost_per_unit[i] × qty[i]
subject to  Σ  nutrient[n][i] × qty[i]  ≥  target_min[n]     ∀ n
            Σ  nutrient[n][i] × qty[i]  ≤  target_max[n]     ∀ n 有上界者
                                qty[i]  ≤  max_qty[i]        ← 适口性上限，见下
                       count(qty[i] > 0) ≥  min_variety      ← 品类下限，见下
                                qty[i]  ≥  0
```

**两条非标准约束，是这个设计成败的关键：**

无约束的 LP 会产出不可食用的解 —— Stigler 1945 年的原始最优解是一年 $39.93 的面粉、卷心菜和干海军豆。
**演示时如果输出「每天吃 2 公斤卷心菜」，可信度当场归零。** 因此：

| 约束 | 取值 | 理由 |
|------|------|------|
| `max_qty[i]` 单食物上限 | 按 basis 分档：蛋白类 ≤300g、蔬果 ≤500g、油脂/调味 ≤50g、补剂按标示剂量 | 阻止 LP 把解压到单一最便宜食物上 |
| `min_variety` 最少品类数 | ≥ 5 | 保证输出看起来像一份食谱，而不是一个数学答案 |

`min_variety` 是基数约束，严格来说会让问题变成 MIP。**v1 不引入 MIP 求解器** ——
先解 LP，若结果品类数 < 5，则对已选中的最便宜食物逐个收紧 `max_qty` 后重解，最多重试 3 次。
这是启发式，不保证全局最优，但在 n=48 的规模下足够，且避免引入 1MB 的 WASM 求解器。

**求解器选型**：`javascript-lp-solver`（~30KB，纯 JS，单纯形法）。n=48、约束 ~25 条，求解在浏览器内 <10ms，可完全客户端运行、无后端。

## 6. 取舍

### 6.1 优化算法

**方案 A — 贪心（按每林吉特营养排序依次取）**
优点：零依赖，实现 2 小时。缺点：可证明次优。演示时懂行的人手算就能找到更便宜的组合，直接击穿「最优」这个卖点。

**方案 B — 线性规划（单纯形）**
优点：给定约束下精确最优，n=48 求解瞬时。缺点：需 30KB 依赖；无约束时产出不可食用解（须靠 §5 的两条约束兜住）。

**方案 C — 整数规划（份量取整，如整颗鸡蛋）**
优点：输出最贴近现实采购。缺点：需 WASM 求解器（~1MB），求解慢，v1 用不上这个精度。

**推荐：方案 B。** 驱动因素是 §1 的主要目的 —— 这是演示资产。
「这是数学上最省钱的吃法」这句话必须站得住，贪心撑不起来；而 C 的取整精度对演示不产生额外说服力，成本却翻倍。

### 6.2 部署位置

**方案 A — 放进 `repos/notes`（Docusaurus）**
优点：复用构建管线、样式、校验脚本、现成部署；数据溯源（USDA FDC ID + `last_verified`）在同一站点内可见。
缺点：docs 站点的 URL 形态对商务受众偏弱。

**方案 B — 独立 Next.js 应用（Vercel）**
优点：干净的产品域名，演示形态最好。缺点：要重建数据管线与部署，多花 ~8 小时；在「渠道方是否感兴趣」尚未验证前就投入产品化包装，与分析文档的结论相悖。

**推荐：方案 A，且这不只是省事的妥协。** 对企业健康计划/保险的技术与采购受众，
**数据可溯源比页面漂亮更能建立信任** —— 每条食物旁边就是 USDA FDC ID 和采集日期，
这正是他们评估一份外部数据源时会问的第一个问题。`optimizer.ts` 保持为无框架纯模块，
一旦有渠道方进入实质洽谈，抬进独立应用是复制粘贴而非重写。

## 8. 验证标准（这是验证工具，本节最重要）

**必须先讲清楚一件事：Web 工具本身证明不了 B2B 需求，洽谈才能。工具是洽谈的输入，不是证据。**
因此判定标准围绕洽谈结果设定，不围绕工具指标。

| 信号 | 判定为「继续」 | 判定为「停止」 |
|------|--------------|--------------|
| **主要 —— 渠道方洽谈**（目标接触 5 家：企业健康计划 / 保险 wellness / HR SaaS） | ≥2 家在看过演示后主动要求后续会议或试点讨论 | 普遍反馈「我们没有这个问题」或「用 MyFitnessPal 就够」 |
| **次要 —— 消费端行为** | 打开页面的访客中 ≥25% 实际跑了一次求解 | <10% 求解率 = 概念本身没吸引力 |
| **数据可信度** | 洽谈中无人质疑价格数据不可用 | 被指出数据太旧/覆盖太窄以致无法评估 → 先补数据再谈 |

「停止」触发时，回到分析文档的结论：全成本口径 EV 为负，不投移动端那 270 小时。
**这个工具的最大价值可能是让你花 30 小时而不是 886 小时得到这个答案。**

## 9. 合规与定位（刻意的设计约束）

分析文档 §5 列出的三条法规硬约束，本工具通过设计规避而非通过合规投入解决：

| 约束 | 规避方式 |
|------|---------|
| **马来西亚 PDPA 2024** —— 健康数据属敏感数据，强制 DPO，罚则 RM250K + 2 年监禁 | **不收集任何个人数据**：无账号、无登录、无服务端持久化，全部计算在浏览器内完成。不触发 PDPA 义务，`docs/analysis` §3.2 那笔 RM 4,000 法务费在验证阶段不产生 |
| **Act 774** —— nutritionist / dietitian 为受保护称号 | 全站文案定位为「**成本-营养算术工具**」：输出是采购组合与价格，不是膳食建议。不出现 recommend / should eat / 营养建议 这类措辞，不使用 nutritionist / dietitian 名义 |
| **埋点可能触碰健康数据** | 只记录**聚合事件**：`optimizer_opened`、`solve_run`、预算落在哪个区间档（分桶，非原值）。**不记录**具体目标值、不记录输出组合、不设会话级用户标识 |

RDA 参照值来自 `rda_reference.yaml`，其文件头已声明为通用成人参考值、非个性化。
页面须原样保留这一免责声明，不得在 UI 上暗示已按个人情况调整。

## 10. 风险

| 风险 | 缓解 |
|------|------|
| LP 输出不可食用组合，演示当场失信 | §5 的适口性上限 + 品类下限；上线前用 5 组真实预算（RM 8 / 12 / 15 / 20 / 30 每日）人工审查输出 |
| 48 条食物不足以支撑可信演示 | 先补齐缺价的 2 条并全量抽查；若洽谈方质疑覆盖度，**这本身就是有效信号**，不是失败 |
| 价格数据 2026-08 采集，会过期 | 页面显式展示采集日期与 `last_verified`；超 3 个月在 UI 上标记为待复核（与 `docs/analysis` 的 re-verify 约定一致） |
| 派生逻辑在 Python / TS 间漂移 | §4 的架构即为此设计：派生只在 Python，TS 只消费 JSON。`nutrition-derived.json` 纳入 `make test` 校验，产物与源数据不一致即失败 |
| 品类约束的启发式重解不收敛 | 最多重试 3 次，仍不满足则如实展示 LP 原解并标注「未满足最少品类数」，不静默返回错误结果 |

**回归范围**：`FoodsExplorer` 是现网页面，增加派生列须重跑其现有筛选/排序/列隐藏行为
（`DEFAULT_HIDDEN_COLUMNS` 的「新列默认隐藏」约定必须保持 —— 文件内注释明确要求不得让默认视图突然多出列）。

## 11. 开放问题

1. **部署位置**：确认 §6.2 推荐的 `repos/notes` 方案？*（提议：是。独立应用留到有渠道方实质洽谈后再做。）*
2. **RDA 基准用哪套**：`rda_reference.yaml` 明确是通用 US/EU DV，但马来西亚有自己的 RNI（NCCFN 发布）。
   面向马来西亚渠道方演示时用美标 DV，是懂行的买家会当场指出的可信度缺口。
   *（提议：v1 沿用现有 US/EU DV 但在 UI 显著标注来源；把「换 RNI」列为洽谈后的第一项数据工作 —— 因为换基准要动 `rda_reference.yaml` 的契约，会波及 `validate-nutrition-data.mjs` 和 `NutrientLookup`，不是改个数字。）*
3. **食物命名语言**：数据里是 `鸡蛋 (egg)` 中英混排。马来西亚受众是马来语/英语。
   *（提议：演示阶段 UI 只显示括号内英文名，不改数据层；是否加马来语名等洽谈反馈再定。）*
4. **数据集广度**：48 条够不够开口谈？*（提议：够 —— 让覆盖度质疑成为一个可观测信号，而不是先花 50 小时补到 300 条再去撞可能根本不存在的需求。）*
5. **埋点工具选型**：需要一个不设 cookie、不做用户识别的方案（Plausible / Umami 自托管）。*（提议：Plausible，因其默认无 cookie、无个人标识，与 §9 的约束天然一致。）*
6. **洽谈名单**：§8 的「接触 5 家」目前没有具体名单。这是本设计之外、但阻塞验证的前置工作 —— 谁来列？
